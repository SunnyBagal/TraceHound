## 2. Golden schema and the multi-file rule

Schema v2 retains `id`, `label`, `file`, inclusive `lines_at_head`, `description`, `category`, `fix_pr_url`, `fix_sha`, `introducing_sha` and `role`; optional provenance fields remain. Clean rows retain their clean label and have no defect golden. Superseded rows are historical, never active input.

For a bug case, **the starting fix's verified bug rows are one bug**, mechanically, as adopted in076 and devin's schema. Every other bug row of that case remains `role: note`, not scored. The canonical row is `role: primary`; other rows of that starting-fix bug are `role: alternate`. This protocol adds no discretionary causal-adjudication step that can drop a verified starting-fix row. The case counts once, and a comment matching any accepted row catches it.

Choose primary mechanically: **the first file among the starting-fix bug's verified rows**, in the order returned by `git show --no-renames --name-only --format= <fix>`. The filter is membership in those verified rows, **not file type**: no verified test/documentation row is excluded for being a test/documentation file. Remaining rows are alternates. Never choose by model output, reviewer outcome, apparent ease or human preference. Apply the same rule on dev and held-out. Within each file, use the **span of overlapping verified ranges of that defect**, from the smallest start to the largest end. A non-overlapping variant of the same starting-fix defect becomes a separate alternate target in that file. Preserve all original range evidence in provenance; each case still counts once (076c item1, Planner B §1.2).

Write role overlays separately from the original labels. Each active bug case must resolve to exactly one canonical primary plus zero or more alternates, with the same fix and introducing head. Record source/provenance and overlay hashes. Two source rows describing the same file/range/defect are not two alternates.

The golden description stays the **label of record's**, not a merged or newly generated description. Name the labeller order explicitly: **dev: grok, bunny, codex, devin; held-out: codex, devin, grok, bunny**. Choose the first active verified row available in that order for the target's file/defect; superseded rows never become active by priority. Apply this named order at the scheduled overlay rewrite even where the current description differs from the first eligible row. Freeze the exact label files, their order and hashes. Apply the span rule to dev before R1 and to held-out at F1; originals and historical blind agreement remain unchanged.

The builder emits one logical **High** golden per bug case, carrying all accepted file/range targets for that defect. A comment matching any accepted row catches the case **once**. The existing title-keyed scorer may be reused only through an adapter that preserves this OR-over-targets rule and stable case keys. It must not inflate the denominator for alternates. Never convert a note into a target merely because it helps a match. Clean cases have no golden.

Schema agreement uses devin's accepted overlap rule: same selected fix, same file and **any inclusive line overlap** counts as agreement; both clean counts as agreement. Exact start-line equality is not required. Agreement is distinct from the ±10-line location-hit metric and from semantic judge matching. New canonicalization must not rewrite the historical blind disagreement rate as though the labels were originally identical.

Attribution status, including moved/unmappable, remains recorded. **The one unmappable case stays in the20** (076c item1, Planner B §1.1). Every tool also gets the fixed sensitivity line **“K of19 without the unmappable case”**; it never replaces the headline and has no test. Unmappable attribution is distinct from invalid geometry. Validate target files/ranges at the frozen head; the builder stops for missing files or out-of-bounds ranges. Before the tag, the labeller of record recomputes any invalid range, the second labeller confirms it, Codex reports count/kind only, and Sunny rules. After the goldens' hash is recorded, labels/overlay/goldens do not change: disclose any later problem without selective repair. Reachability in a rendered chunk remains a separate measurement.

## 3. Counted comments and collection

Adopt the existing rule in `packages/analyzer/src/bench/convert.ts`: **top-level line-level review comments from the intended tool's bot/tool account**. Exclude replies, summaries/walkthroughs, review-body sections, issue comments, PR-description summaries, humans and unrelated bots. This is no extension of the old output-type rule. The new collector tightens identity to each tool's frozen allowlist rather than accepting every account whose GitHub type is Bot.

Freeze an explicit per-tool API `user.login`/`user.type` allowlist after G1/S1 observes real comments. A mention handle or App slug alone is not evidence of API identity. Collect and archive all raw relevant API objects as evidence, then apply the rule; an excluded summary is not an actionable comment for scoring. Every counted GitHub comment is counted once by immutable object ID. Preserve original body, file, current/original line, review ID, author, commit binding and timestamps. Do not include later revisions created outside the window.

Before judging, report per tool the number of top-level line comments excluded as other author and the number of distinct Bot logins behind them. Non-zero: Sunny rules, before any score exists, whether a login belongs to the tool; log the ruling and any re-collection (U5). Do not silently expand an allowlist after seeing a score.

TraceHound is scored from its **local neutral finding export**, one proposed comment per finding the frozen product would emit, not the single optional PR body wrapper. Use only official successful-case output; exclude diagnostics, pool candidates dropped before posting, fix suggestions and usage/footer text. Apply the frozen15-comment model-finding cap in pool order. **Contracts are OFF by B3's ruled recommendation criterion:** the40-case dev audit found0 findings and0 label hits (typed stage skipped-budget in37 cases, a recorded limitation). With no label hit the plan's “on only if≥1 hit and≤1 finding/case” condition fails. Fixes are off. If a later separately ruled configuration enables contracts, every emitted contract finding must also be exported with product dedupe; a model-only export would then be incomplete.

For each tool/case, record completion separately from comment count. **Completed = any review object, inline comment or issue comment by the tool's listed bot login, after that PR's trigger and inside the window, except a rate-limit, error or not-completion message** (076c U1, amended by076d item2). **“In progress”, “review skipped”, “paused” and similar placeholder/status messages are not completion.** S1 and P1 record their exact text; put these patterns in each tool's `notCompletion` list in `scripts/testset/tools.json` alongside rate-limit/error patterns, and freeze the lists after P1. Retain the API evidence. Read issue comments **for completion only**: they never enter counted findings, location hits or comment totals. A completed review with zero eligible inline comments is a valid zero. S1 also triggers Greptile on one clean dev case (one credit, $0 Nebius;076c item8); S1/P1 report per tool “zero-inline completion seen: yes/no; marking object”. If evidence is absent and no ruling covers it, F1 stops rather than inventing a completion marker.

The collector must receive exactly one explicit completion bound: `--resume-file` for first-trigger evidence, or `--bound window-start` for cases with no trigger record (076d item4). With neither it refuses. The window-start collection is a recorded deviation and **never drives a re-trigger**. Re-trigger evidence must use first-trigger provenance and cover the full first24h: `window.start <= firstTrigger` and `min(window.end, collectedAt) >= firstTrigger + 24h`. A late collection timestamp alone does not prove that coverage.

Collection records exact PR/base/head, tool/configuration revision, timestamps and SHA256 of raw/neutral artifacts. Check PR base/head binding; do not substitute a new tip. **invalid-binding becomes no-review for that tool**, excluded from its pairs with n reported (U6). **read-failed is not a result**: repeat collection into a new directory until it reads; the last complete collection is official. Preserve all attempts and the fixed review window; re-collection gives no extra review time. Normalize statuses in a recorded adapter before scoring if the frozen scorer does not accept the collector's raw status. Snapshot at the fixed window end, equally for every tool.

## 4. Scoring, denominators and reporting

Primary metric: **distinct labelled bugs caught**, with a Wilson95% interval **without continuity correction**. Headline includes tool/case completion coverage, comments per PR and TraceHound cost per PR. F is a dev diagnostic only, never the held-out headline.

- One caught bug per case at most, regardless of matching comment count or target-row count. Judge match to any primary/alternate target establishes the logical match. Do not add extra TP for a second matching comment or alternate.
- Primary judge: frozen `bench-judge-v1`; secondary judge: frozen `bench-judge-x1` (Qwen3-235B-A22B-Instruct-2507, not Claude). Use existing prompt/model/settings; hash exact configurations at freeze. E1 also uses x1 on dev (076g item3); preserve separate judge rows. No E1 result selects a replacement for frozen A0. Secondary judge rows remain report-only.
- At most one re-run per judge process; the later detail file is official for that row (U9). Retain/hash both files and charge both to the job. A JUDGE_FAILED case sends all its comments to the sheet. Judge re-runs do not change the frozen prompt or allow extra tool reviews.
- Report `K/20` as ruled inS0.3, with review completion/failure coverage visible. An unavailable review supplies no caught bug; do not replace the headline denominator with completed reviews. Any completed-review ratio is a separately labelled diagnostic, never a substitute for `K/20`.
- For a tool with no review after its permitted re-trigger, exclude that case from **that tool's paired comparison** and report the pair's n and exclusions (076a §13.4). TraceHound's failed/twice-failed and unstarted-at-window-end cases follow section9's miss rule. Do not turn a missing external review into a completed zero merely to keep paired n constant.
- **Registered held-out primary pairs: Nemotron A0 vs CodeRabbit; Nemotron A0 vs Greptile** (076c U3). Each uses the **exact two-sided sign test on discordant bugs** (exact McNemar), **α=0.05, uncorrected across the two tests**: if a is caught only by A and b only by B, `p = min(1, 2 * P[Binomial(a+b, 0.5) <= min(a,b)])`; if a+b=0, p=1. Report exact p-values for eligible registered pairs and name the two uncorrected tests in the limits. No mid-p, asymptotic test, familywise guarantee, rank or equivalence claim. CodeRabbit vs Greptile is **counts only**; A1/A2 and the Claude dev rows are never tested. The separately registered A0 pooled analysis below is secondary and does not change these held-out primary comparisons.
- **G10 floor: fewer than15 of20 bug cases completed by both tools → counts only, no test sentence** (076c item6). Record the number actually reviewed by both separately from the paired eligible n: a retained TraceHound failure/miss does not count as a completed review merely because it remains in a pair. Above the floor, the exact test still does not establish equivalence on non-rejection.
- Report the fixed **K/19 without the unmappable case** sensitivity for every tool, with no test and no substitution of denominators.
- Report each tool's **exposed: K/E bug cases caught; unexposed: K/(20−E) bug cases caught**, separately (076d item1d, addendum (e); 076e item4). Judge exposure **per review at its actual time from the scheduler's branch log**, with the fork's branches logged before every trigger/re-trigger command; do not classify from planned slot order. Pair a snapshot with the resume file's `triggered:<tool>` / `retriggered:<tool>` records and corresponding logged command; a command snapshot alone does not prove a review was triggered. Construct **one common exposed set: the union over CodeRabbit's and Greptile's reviews**, including reviews following re-triggers. Use that identical per-bug yes/no set for TraceHound, CodeRabbit and Greptile; no per-tool exposed sets or scorer change. Preserve and hash the private per-review audit and common exposure input before scoring; reports contain counts only. No case is excluded. If E=0, report **0/0 (no exposed bug cases)** rather than an exposed catch rate. These are counts-only diagnostics, with no additional test. Later-branch visibility at a delayed review or re-trigger remains a stated limitation; the historical planned-order zero is not a fixed first-review grouping for executed reviews.
- Report total eligible comments, mean/median comments per attempted PR and per completed PR, clean-case comment counts, completion/failure/partial counts, and cost mean/median/max plus total. Distinguish pipeline, judging and infrastructure costs. Contract/model sources remain visible in aggregate diagnostics.
- Label-match fraction is a **lower bound** on precision: unlabelled valid defects can be counted against a tool. It does not estimate all-bug recall or prove clean cases bug-free. Never choose comment inclusion after scoring.

## 6. Power and claim templates

Six net bugs is the minimum observed gap that can be significant at20 bugs, not a guaranteed significance rule: discordant splits6–0,8–1 and10–2 differ. A true gap and an observed gap are different quantities.

Under bunny's independent-catch examples,20% versus50% and15% versus45% recall give exact-test power0.37–0.39 at n20, α0.05. For20% versus50%, power rises to0.44/0.53 at catch correlations0.2/0.4. Baseline recalls and correlations on TS are unmeasured. Approximate gap/power estimates from that model are not empirical requirements or promises of detection.

S0.3 fixes the **metric**: bugs caught of20 with a Wilson interval, comments per PR and cost per PR; F on dev only. Claim template: “On29 held-out PR cases from **medusa (8), payload (10), twenty (10), and bullmq (1)**, Tool T caught K/20 labelled bugs (Wilson interval L–U), posted a mean C eligible comments per completed PR (n completed; mean per attempted PR also tabulated) and cost D per attempted PR.” These are exactly the repos with at least one held-out case (076a §13.8); the older two-repo paragraph is superseded. Counts-only population check: medusa5bug/3clean, payload7/3, twenty7/3, bullmq1/0 =20bug/9clean. Fill results from frozen records and the blind hand-check, not forecasts. This describes selected later-fixed-defect cases, not all bugs or PRs in those repos.

For a registered pair meeting the15-reviewed-by-both floor, if the exact test does not reject, say **“no detectable difference at this sample size.”** Below the floor say **“counts only: too few cases reviewed by both tools for a test sentence”**, with no outcome A/B/C inference. Never claim equivalence or a rank. If a registered test rejects, describe that pair, observed gap, n and exact p, naming the two held-out uncorrected tests and their limits. If pooled secondary tests are also presented, name all four uncorrected comparisons and keep the pooled inference secondary. State selection history, limited labels, exclusions and context/ref visibility limitations.

Historical cost is about **$0.075 per PR measured on non-TypeScript dev** (budget/results); any TS cost before live measurement is labelled **estimate**. Do not call about$0.08 a measured TS cost. Report actual ledger and console reconciliation separately after runs.
