## 1. What the kit does
Label rows → one golden per case → each tool's counted comments as neutral review files → judge detail → the tables
(bugs caught of N with a Wilson interval, comments per PR, location hits, cost, pairwise exact sign test) → the blind
hand-check sheet → the final tables with the hand-check's decisions. No model call is made by the kit itself; the judge
runs through `tracehound bench score`.

## 4. Rules the kit must enforce (each one has, or must get, a test)
1. **Side guard.** `--side dev` refuses any input or output path that has a `heldout` segment after symlinks are
   resolved, including a not-yet-existing output under a symlinked parent. Exit 2, nothing written.
2. **Never overwrite.** Every output is written only if absent; otherwise exit 2.
3. **stdout is counts only.** No comment text, no label text. `build-goldens` may name a case id in a preflight error.
4. **One golden per bug case, none per clean case.** Targets = the overlay's rows for that case: exactly one `primary`,
   first, then `alternate`s. The build checks that the primary is the first of the rows in the order of
   `git show --no-renames --name-only --format= <fix>` and refuses otherwise; it never re-chooses (decision 076 S0.1).
5. **Preflight.** Every target file exists at the case head and its range is inside the file; one label of record per
   case; unique PR titles. Any failure: exit 2, nothing written.
6. **Counted comment** (ts-protocol §3): author login is in the tool's configured list (case-insensitive), it is a
   top-level line-level review comment, created inside the window, made on the case head. Counted once by id. Everything
   else is excluded and counted by reason.
7. **Completion (decision 076c item 2, question U1; amended by 076d items 2 and 4).** `completed` = by a listed login, after the completion bound
   and inside the window: a review object on the case head, or an inline review comment, or an issue comment; except a
   message that matches one of the tool's `notCompletion` patterns (rate-limit and error messages, and since decision
   076d item 2 also "in progress", "review skipped", "paused" and similar messages, §5.3). Otherwise
   `no-review`. Issue comments are read **for completion only**; they are never counted comments (rule 6 is unchanged).
   **The completion bound is explicit (decision 076d item 4; codex's finding P2-1):** exactly one of `--resume-file`
   (the bound is the tool's first `triggered:<tool>` record for the case; a listed case without one refuses) and
   `--bound window-start` (the bound is the window start; only for cases whose tool was never triggered) must be given.
   With neither, or with both, the collector refuses before any read. The collection file records which applied
   (`completionFrom`: "first trigger (--resume-file)" or "window start (--bound window-start)"). A `--bound
   window-start` collection is a deviation to report; it is not evidence of "after the trigger", and `open-prs.ts
   --retrigger` refuses it. **`--never-opened <ids>`** (only with `--bound window-start`) names cases whose PR never
   opened: each is written as `no-review` without any `gh` call and listed in the collection file (`neverOpened`); an id
   named there that has a PR number in `--pr-map` refuses, and a case with no PR number that is not named there still
   refuses, so a gap in the PR map is never read as "never opened". A PR whose base or head is not the case's
   pair is `invalid-binding`; a PR that could not be read is `read-failed`. Implemented in `collectCase`,
   `triggerTimes` and `main` of `scripts/testset/collect-tool-reviews.ts` (header and constants
   `COMPLETION_FROM_TRIGGER`, `COMPLETION_FROM_WINDOW_START` at `b696231`, on `main`). A CodeRabbit rate-limit comment never makes a case `completed`
   (https://docs.coderabbit.ai/management/rate-limits: "The comment is the authoritative signal that no review ran"),
   now because its wording is a `notCompletion` pattern, no longer because issue comments are unread.
8. **A catch counts once per case**, whatever the number of matching comments or targets.
9. **Judge evidence is bound.** Without `--handcheck`, every completed bug case needs its entry in the judge detail,
   and the judged comments must equal the review's comments in order. A gap refuses the run (exit 2); it never becomes
   a miss. `JUDGE_FAILED` is counted and is never a catch.
10. **Pending choices only through `--policy`.** No default. The policy file and its sha256 are written into the output.
11. **Pairs (decision 076c items 4 and 6; built at `82b65e4`, header of `score-testset.ts`).** Every pair of tools gets
    counts: paired n, reviewed by both, only-A, only-B, both, neither. A p-value (exact two-sided sign test on the
    discordant cases, uncorrected) is computed only for a pair the policy registers (`registered_tests.pairs`) and only
    when at least `registered_tests.min_reviewed_by_both` bug cases were reviewed by both tools (both statuses
    `completed`; a miss by rule stays in the paired n but is not a reviewed case). Every other pair, and every pair
    when the policy registers none, has `p: null`; the summary carries no other p. A registered tool that is not a
    `--tool` refuses, which is why the dev arm jobs keep `policy.076a.json` (no `registered_tests`) and S1 and H2 use
    `policy.076c.json` (pairs tracehound–coderabbit and tracehound–greptile, `alpha` 0.05, floor 15). No verdict is
    printed by the kit.
11c. **Exposed / unexposed split (decision 076d item 1d; `--exposure`, `82b65e4`).** With `--exposure <file>`
    (`{v: 1, exposed: [bug case id, …]}`) every tool gets two count lines: bug cases, caught and completed on the
    exposed cases and on the unexposed ones; the summary records the file's sha256 and the two set sizes. An id that is
    not a bug case of the goldens, or one listed twice, refuses. The file is made and kept on the held-out side (codex);
    the dev side never sees it. **One file marks the same cases for every tool of that run**, so the two
    groups have the same denominators for every tool. Decision 076d's addendum (e) judges exposure per review at its
    actual time, which can differ between two tools on one case (a re-trigger comes later than a first review);
    `docs/runbooks/H2-scoring.md` §1.5 says how the one set is made from the per-review flags.
11b. **Scorer statuses (question U6, 076c items 5 and 9; `main` → `toStatus` in `score-testset.ts` at `6fd4568`).** The
    collector's `invalid-binding` is scored as `no-review` for that tool: out of its pairs, counted in
    `tools.<t>.invalidBinding`, printed as "no-review N (invalid-binding k)". `read-failed` is not a result: exit 2, no
    output; the collection is repeated into a new directory and the last complete collection is official.
12. **Sheet blindness.** Items of all tools and cases are shuffled together by a recorded seed. The sheet shows the
    labelled bug, the locations and the comment body: no tool name, no judge outcome (policy `sheet_judge_cues: hidden`),
    no reason the item is listed. `mapping.json` is private. `hashes.json` holds the sha256 of sheet, decisions,
    mapping and the recipe (seed, strip patterns).
13. **Guess column (decision 076c item 7; `buildSheet` and `resolve` in `handcheck-sheet.ts` at `595707f`).** Every
    item of `decisions.json` has `guess: null`; the sheet still names no tool. `resolve` requires a guess on every item
    (a `--tool` name, case and spaces ignored, or `unsure`), refuses otherwise (exit 2, nothing written), and writes
    counts only. `score-testset.ts --handcheck` prints one line and writes `handcheckGuess`.

- **`logins`** are copied from the `user.login` of real review comments read in S1 (`docs/specs/S1.md` step 6). grok saw
  `coderabbitai[bot]` on public PRs; Greptile's comment login is unobserved (`run/out/grok.tool-facts.md` rows 9, 14).
  Do not write this file from those rows.
- **`notCompletion`** is a list of regular expressions, matched case-insensitively against the body of a review object
  or an issue comment. A message that matches is one of the not-completion kinds below and does not complete a review
  (rule 7). The list is **required per tool**; an explicit `[]` is allowed and means "no such message is known"; a missing
  list or a pattern that is not a valid regular expression refuses. The patterns in force are written into
  `<tool>.collection.json` with every collection.
- **Which messages go in (decision 076c item 2, widened by 076d item 2):** a rate-limit message; an error or failure
  message; and a message saying "in progress", "review skipped", "paused" or similar, that is, any bot message whose
  own words say that no review has been delivered (yet, or at all) for this request. A walkthrough, a summary, a "no
  issues found" text or a reply to a command is **not** such a message.
- **Where the patterns come from, and when they freeze.**
  1. S1 writes the file with the logins and, per tool, a pattern for each such message **actually seen** in S1; a
     tool with none seen gets `[]`. S1 and P1 save the **exact text** of every such message (`$J/not-completion/` in
     `docs/specs/S1.md` step 6 and `docs/specs/P1.md` §2), and each pattern names the saved file it was written from.
  2. P1 adds CodeRabbit's messages as seen on the ladder (`docs/specs/P1.md` §2). A pattern is the message's fixed
     wording, anchored enough not to match a walkthrough or a summary; no PR-specific text. **A placeholder that the
     bot later edits into its final comment needs care:** the pattern must match the placeholder's wording and must not
     match the final comment, or a finished review becomes `no-review`. Check each pattern both ways: it matches its
     saved text, and it matches none of the walkthrough, summary or "no issues" bodies in the dev raw files
     (`grep -i -E -c` over `$J/tools-*/raw/`, expected 0). A pattern that fails the second check is not used; the
     case goes to Sunny.
  3. A message that a vendor documents but that was never seen may be added only as the documented wording, with its
     URL, marked "documented, not observed" in the commit message. The one known candidate is Greptile's failure text
     (`run/out/grok.tool-facts.md` row 13; `run/out/bunny.076c.md` step 1). Nothing else is written from memory.
  4. A bot message that does not mean "a review ran" but is none of the named kinds and not plainly similar (for
     example a notice that only part of the diff was reviewed) is not added on anyone's own decision: it goes to
     Sunny with its saved text's sha256 and its count (`docs/specs/S1.md` §3, `P1.md` §2).
  5. **The real patterns are frozen after S1 and P1, with the logins** (decision 076d item 2: "the lists freeze after
     P1"): the last change to `tools.json` is the commit
     after P1's report; codex checks each pattern against the evidence named for it; the file's sha256 goes into
     `docs/bench/ts-freeze.md` at F1 and the file does not change again. No pattern is added during or after the window.
  6. After the last change the dev collection is made once more, into a new directory, so that the dev status files L1
     reads were produced by the frozen list (the collector never overwrites; the earlier collections are kept).

## 9. The three most likely ways to get this wrong
1. **Turning missing data into a miss.** A missing judge entry, a missing review file or a rate-limited request must
   stay "no evidence" (refuse, or `no-review`). Only a completed review that the judge scored, or a twice-failed
   TraceHound case, can be a miss.
2. **Counting a bug twice or widening the denominator.** Alternates are OR-targets of one golden. N is 31 on dev and 20
   on held-out, never 34 or 21.
