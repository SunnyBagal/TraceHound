## 2. Trigger CodeRabbit and measure the rate (the ladder)
One trigger = `cd $TS && node scripts/open-prs.ts --manifest cases/dev/manifest.json --fork SunnyBagal/$R --trigger coderabbit --ids <one id> --execute`.
Never pass `greptile` or `bugbot`. The script itself refuses more than 10 triggers per rolling hour per tool
(`TRIGGER_PER_HOUR = 10`, `scripts/open-prs.ts:57`).

Log every trigger in `$J/triggers.tsv`: `utc_time  repo  case  pr  level  outcome  minutes_to_outcome  remaining_shown`.
**Outcome**, read 30 minutes after the trigger (and again at 60 if still nothing). The definition is decision 076c
item 2 (question U1), amended by decision 076d item 2: a review is completed if the tool's bot posted any review object,
inline comment or issue comment on the PR after the trigger, except a rate-limit or error message **and except a
message saying "in progress", "review skipped", "paused" or similar**. Read each PR at 5, 15 and 30 minutes too: a
placeholder may be edited into the final comment, and its text is then gone.
- `reviewed`: after the trigger, the CodeRabbit login of `tools.json` posted a review object, an inline review comment,
  or an issue comment that is not one of the not-completion messages below;
- `rate-limited`: CodeRabbit posted its rate-limit comment ("the comment is the authoritative signal that no review
  ran", https://docs.coderabbit.ai/management/rate-limits). Record the wait time it states, and copy the comment's
  fixed wording (no PR-specific part) for the `notCompletion` list (`docs/specs/B2.md` §5.3);
- `error`: the bot posted an error or failure message and nothing else. Same: copy its fixed wording;
- `not-completed`: the only bot objects are "in progress", "review skipped", "paused" or similar messages (decision
  076d item 2: not a completed review). Log which kind;
- `nothing`: no bot object after 60 minutes.
For every trigger also log the **kinds** of issue comment the bot posted (walkthrough or summary, "no issues" text,
in-progress placeholder, "review skipped" notice, "paused" notice, rate-limit, error, reply to a command).
**Exact text (decision 076d item 2).** The first time each distinct not-completion message is seen (rate-limit, error,
in progress, skipped, paused, anything similar), and again whenever its wording differs from a saved one, save the
body as it is: `gh api --method GET repos/SunnyBagal/$R/issues/comments/<comment id> --jq .body > $J/not-completion/coderabbit.<kind>.<n>.txt`
(a review body: `repos/SunnyBagal/$R/pulls/<n>/reviews/<review id>`). List each file in `$J/triggers.tsv`'s notes with
its sha256, the reading at which it was seen and whether a review followed. The `notCompletion` patterns are written
from these files and S1's (`docs/specs/B2.md` §5.3), never from memory or documentation. A message that is none of the
named kinds and not plainly similar goes to Sunny before the patterns are frozen; P1 does not decide it.

**Ladder (levels are triggers per rolling hour, all inside one repository, at least 5 minutes apart):**

| hour | repository | level | go on if |
|---|---|---|---|
| 1 | medusa | 2 | both `reviewed` |
| 2 | medusa | 3 | all `reviewed` |
| 3 | medusa | 5 | all `reviewed` |
| 4 onward | medusa until done, then twenty, then payload | 10 | all `reviewed` |

Rules, fixed now:
0. **The re-trigger command (premortem gap G5; decision 076c items 3 and 9).** The re-trigger mode of `open-prs.ts`
   is on the testset repo's `main` (`060c644`; functions `runRetriggers` and `readCollectorStatus`; codex's GO on patch
   sha256 `32085be3…5900`), so no `gh` line is typed by hand. P1's re-trigger is, 24 h or more after the PR's own
   trigger: first the collector for that case
   (`collect-tool-reviews.ts … --tool coderabbit --ids <id> --window-start <the window start of §3> --window-end <UTC now> --resume-file $TS/run/open-prs/$R.resume.jsonl --out $J/check/<id>`),
   then `cd $TS && node scripts/open-prs.ts --manifest cases/dev/manifest.json --fork SunnyBagal/$R --resume-file run/open-prs/$R.resume.jsonl --retrigger coderabbit --status $J/check/<id>/coderabbit.status.json --ids <id>`
   (dry run, then `--execute`). The mode re-triggers only a `no-review` case that is due and never posts a third
   trigger. It also checks what the collection covered (decision 076d item 4; header of `scripts/open-prs.ts` at
   `060c644`): the completion bound must be the first trigger (so `--resume-file`, never `--bound window-start`), the
   window must start at or before that case's first `triggered:coderabbit` record, and the earlier of the window end
   and the collection time must be at least 24 h after it. P1 is the mode's first real use, so its dry-run and execute
   output go into the report. Log the re-trigger in `$J/triggers.tsv` with outcome column `retrigger`.
1. The first `rate-limited`, `error`, `not-completed` or `nothing` outcome ends the climb. Wait the stated time (60 minutes if none is
   stated), then continue with the **next** PR **at the last level whose hour was all `reviewed`** (level 1 if hour 1
   failed) for the rest of P1. The PR that got no review is **not** re-triggered then. Decision 076c item 3 (question
   U2): a PR is re-triggered only if it has no completed review 24 h after its own trigger; a completed review with
   zero comments is never re-triggered. So at 24 h after its own trigger, look at that PR again; if it is still not
   `reviewed`, post rule 0's re-trigger, once, counted in that hour's level.
2. **Per-repository test, once:** in the first hour in which medusa's allowance was shown to be exhausted (a
   `rate-limited` outcome), post one trigger on a **twenty** PR within 10 minutes of that outcome. `reviewed` means the
   allowance is not shared across repositories; `rate-limited` means it is. If medusa is never rate-limited, the test is
   NOT RUN and the report says so.
3. A PR still without a completed review at the collection of §3 is a `no-review` case. Never a third trigger.
4. Order inside a repository is manifest order. Do not skip a PR because it is large.
5. At every trigger also record the number of CodeRabbit reviews delivered in the trailing 7 days (count of `reviewed`
   rows, plus S1's), because CodeRabbit lowers the refill rate of its paid plans with 7-day activity and does not
   document the OSS case (plan-v2 F-f). **Decision 076b item 3:** P1 records the hourly rate at its start and at its
   end. *Rate at start* = the highest level whose hour was all `reviewed` during the climb. *Rate at end* = the number
   of `reviewed` triggers in the last full hour of triggering in which at least that many were posted, with no
   `rate-limited` outcome in it; if that hour had one, the rate at end is the number reviewed before it. **Shrank** =
   rate at end < rate at start, or any `rate-limited` outcome at a level that an earlier hour of P1 had passed. If it
   shrank, the held-out window starts at least 7 days after P1's last review; the report gives that review's UTC time.
6. On the first **payload** PR, **after its outcome has been read as `reviewed`** (the reply is a bot issue comment
   and would otherwise itself mark the PR completed), also comment `@coderabbitai configuration` and keep the reply: payload's own
   `.coderabbit.yaml` is in the case heads (`docs/live-setup.md:33-34`), so CodeRabbit runs payload cases under that
   file. That is a stated limitation, not something to change.

Duration (estimate): about 7 hours of triggering if level 10 holds; about 39 hours at 1 per hour; plus 24 hours for
any PR that needs the re-trigger.

`--resume-file` (since `4db9abe`) sets "after the trigger" to each case's own first `triggered:coderabbit` record; a
listed case without that record refuses, so every dev case must have been triggered first (a dev case that could not
be triggered is collected in its own run with `--bound window-start`, and reported as a deviation; decision 076d
item 4). **Before this collection, `scripts/testset/tools.json` gets its final `notCompletion` lists** (the rate-limit,
error, in-progress, skipped and paused wordings saved in §2 and in S1, `docs/specs/B2.md` §5.3 points 2–5); this
collection is the one made with the frozen list (point 6). **The lists freeze after P1** (decision 076d item 2).
The collector writes one status file per `--out`, so each repository gets its own directory and the three are merged by
the last two lines. If the collector refuses a manifest with other repositories' cases, pass `--ids` with that
repository's ids.

Pass: `jq 'to_entries|group_by(.value)|map({(.[0].value): length})|add' $J/coderabbit.status.json` shows
`completed` ≥ 30 of 40, or the report states the limit that stopped it. `invalid-binding` must be 0. A `read-failed`
case (the collector then exits 1) is not a result: collect that repository again into a new directory.

## 3b. Delete the dev case branches from the four forks (decision 076d item 1b)
**When:** after §3's collection passed and its files are hashed, and after every later use of a dev PR by a tool is
over (a pending 24 h re-trigger of rule 1 is collected first). **Before T0**, and before F1 §1 row 16 is checked.
Nothing on the forks is needed afterwards: the collected raw objects are in `$J`, and a closed PR's comments stay
readable.
**What:** every `cases/<id>` and `cases/<id>-base` branch of every dev case, S1's two cases included, on
`SunnyBagal/{medusa,payload,twenty,bullmq}` (bullmq has no dev case; it is checked, not assumed). Deleting a PR's
branches closes the PR; that is expected.
```sh
( cd $J && find tools-* coderabbit check not-completion -type f | sort | xargs shasum -a 256 > hashes.p1.txt && shasum -a 256 hashes.p1.txt )
cd $TS && for R in medusa payload twenty bullmq; do
  U=https://github.com/SunnyBagal/$R.git
  git ls-remote --heads $U 'refs/heads/cases/*' > $J/branches.before.$R.txt       # sha <tab> ref
  # every remote case branch must equal the local clone's ref of the same name, so the deletion can be undone by a push
  [ "$R" = bullmq ] || while read sha ref; do [ "$(git -C repos/$R rev-parse $ref)" = "$sha" ] || echo "DIFFERS $ref"; done < $J/branches.before.$R.txt
  wc -l < $J/branches.before.$R.txt
done
```
Expected counts: medusa 32, payload 18, twenty 30 (two branches per dev case: 16, 9 and 15 cases, §1), bullmq 0. A
`DIFFERS` line, a branch whose id is not in `cases/dev/manifest.json`, or any `cases/` branch on bullmq: **stop and
report; delete nothing**. Then, one repository at a time, dry run first:
```sh
REFS=$(cut -f2 $J/branches.before.$R.txt | sed 's#^#:#')            # ":refs/heads/cases/<id>" deletes that branch
git -C repos/$R push --dry-run --no-verify https://github.com/SunnyBagal/$R.git $REFS | tail -3
git -C repos/$R push --no-verify https://github.com/SunnyBagal/$R.git $REFS
```
(`open-prs.ts` has no delete mode: its `assertGit` allows only the push of a case's two refs, `scripts/open-prs.ts` at
`060c644`. So this is a plain `git push` of delete refspecs, typed from this spec; if bunny makes it a script, decision
076d's Touches list, the script replaces these lines.) The local clones keep every ref: nothing is deleted locally.

**Check that no dev branch remains (counts only):**
```sh
for R in medusa payload twenty bullmq; do
  echo "$R cases-branches=$(git ls-remote --heads https://github.com/SunnyBagal/$R.git 'refs/heads/cases/*' | wc -l | tr -d ' ') open-prs=$(gh pr list --repo SunnyBagal/$R --state open --json number --jq length)"
done
```
Pass: four lines, each `cases-branches=0 open-prs=0`. Anything else: stop; F1 does not start. The four lines go into
the report (§4 item 9) with their UTC time. **This check is repeated in F1 §1 row 16 and in H1 §1**, because the forks
must still be empty of case branches when the first held-out branch is pushed.

**What the deletion does not remove (stated, not fixed; `docs/runbooks/W1-writeup.md` §4 limit 6):** GitHub keeps a
read-only `refs/pull/<n>/head` for every PR ever opened, closed ones too
(https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/checking-out-pull-requests-locally),
so the dev case commits stay fetchable by anyone who asks for those refs, and the closed PR pages stay public. A
default clone does not fetch them. Report the count: `git ls-remote https://github.com/SunnyBagal/$R.git 'refs/pull/*/head' | wc -l`
per fork. A tool that indexed a fork while the dev branches were on it may also keep what it read.

## 6. The four most likely ways to get this wrong
1. **Climbing faster than the ladder.** Ten triggers in the first hour can exhaust an allowance of 1 and leave nine
   rate-limit comments; the measurement is then "below 10" and nothing more. One level per hour.
2. **Counting a rate-limit, error, in-progress, skipped or paused message as a review, or re-triggering a finished
   one.** Any other bot object after the trigger means `reviewed` (076c item 2, 076d item 2), including a walkthrough
   with no inline comment; such a PR is never
   re-triggered (item 3). The collector's status file, not the trigger log, decides `completed`.
3. **Letting Greptile run.** A `greptile` trigger, or an automatic review after opening a PR, spends held-out credits.
   The auto-review check in §1 exists for this.
4. **Deleting before collecting, or deleting something else.** §3b runs only after §3 passed and is hashed; it deletes
   only refs that `git ls-remote` listed under `refs/heads/cases/` and that equal the local clone's refs. A fork's
   default branch and tags are never touched (F1 §1 row 9 checks the default branches again).
