## 1. Open the PRs (per repository; dry run, then `--execute`)
```sh
cd $TS && for R in medusa payload twenty; do
  node scripts/open-prs.ts --manifest cases/dev/manifest.json --clone repos/$R --fork SunnyBagal/$R            # dry run
done
# read the three dry runs; then, one repository at a time:
node scripts/open-prs.ts --manifest cases/dev/manifest.json --clone repos/$R --fork SunnyBagal/$R --execute
```
- The script opens at most 10 PRs per run with a 60 s delay and skips cases already in the resume file
  (`scripts/open-prs.ts:7`, `--batch 10 --delay-ms 60000`); run it again until the dry run lists nothing to do.
  Expected totals with S1's PR: medusa 16, payload 9, twenty 15 (`.agents/STATE.md:21`).
- Before the first `--execute` in a repository, re-check that Actions are off (`docs/live-setup.md` §3).
- **Auto-review check, 15 minutes after the first batch:** for every PR just opened,
  `gh api --method GET repos/SunnyBagal/$R/issues/<n>/comments --jq '.[].user.login'` and
  `…/pulls/<n>/reviews --jq '.[].user.login'` must print nothing. If any bot commented without a trigger, **stop opening
  PRs** and report: an automatic Greptile review spends a credit, and an automatic CodeRabbit review spends allowance.
- Pass: `gh run list --repo SunnyBagal/$R` is empty; every PR is `cases/<id>-base ← cases/<id>`; no PR targets the
  default branch.

## 2. Trigger CodeRabbit and measure the rate (the ladder)
One trigger = `cd $TS && node scripts/open-prs.ts --manifest cases/dev/manifest.json --fork SunnyBagal/$R --trigger coderabbit --ids <one id> --execute`.
Never pass `greptile` or `bugbot`. The script itself refuses more than 10 triggers per rolling hour per tool
(`TRIGGER_PER_HOUR = 10`, `scripts/open-prs.ts:57`).

Log every trigger in `$J/triggers.tsv`: `utc_time  repo  case  pr  level  outcome  minutes_to_outcome  remaining_shown`.
**Outcome**, read 30 minutes after the trigger (and again at 60 if still nothing):
- `reviewed`: a review object or an inline review comment by the CodeRabbit login of `tools.json` exists on the PR;
- `rate-limited`: CodeRabbit posted its rate-limit comment ("the comment is the authoritative signal that no review
  ran", https://docs.coderabbit.ai/management/rate-limits). Record the wait time it states;
- `nothing`: neither after 60 minutes.

**Ladder (levels are triggers per rolling hour, all inside one repository, at least 5 minutes apart):**

| hour | repository | level | go on if |
|---|---|---|---|
| 1 | medusa | 2 | both `reviewed` |
| 2 | medusa | 3 | all `reviewed` |
| 3 | medusa | 5 | all `reviewed` |
| 4 onward | medusa until done, then twenty, then payload | 10 | all `reviewed` |

Rules, fixed now:
1. The first `rate-limited` or `nothing` outcome ends the climb. Wait the stated time (60 minutes if none is stated),
   re-trigger that PR once, and continue **at the last level whose hour was all `reviewed`** (level 1 if hour 1 failed)
   for the rest of P1.
2. **Per-repository test, once:** in the first hour in which medusa's allowance was shown to be exhausted (a
   `rate-limited` outcome), post one trigger on a **twenty** PR within 10 minutes of that outcome. `reviewed` means the
   allowance is not shared across repositories; `rate-limited` means it is. If medusa is never rate-limited, the test is
   NOT RUN and the report says so.
3. If a PR is still `nothing` 60 minutes after its second trigger, leave it; it is a `no-review` case.
4. Order inside a repository is manifest order. Do not skip a PR because it is large.
5. At every trigger also record the number of CodeRabbit reviews delivered in the trailing 7 days (count of `reviewed`
   rows, plus S1's), because CodeRabbit lowers the refill rate of its paid plans with 7-day activity and does not
   document the OSS case (plan-v2 F-f). **Decision 076b item 3:** P1 records the hourly rate at its start and at its
   end. *Rate at start* = the highest level whose hour was all `reviewed` during the climb. *Rate at end* = the number
   of `reviewed` triggers in the last full hour of triggering in which at least that many were posted, with no
   `rate-limited` outcome in it; if that hour had one, the rate at end is the number reviewed before it. **Shrank** =
   rate at end < rate at start, or any `rate-limited` outcome at a level that an earlier hour of P1 had passed. If it
   shrank, the held-out window starts at least 7 days after P1's last review; the report gives that review's UTC time.
6. On the first **payload** PR also comment `@coderabbitai configuration` and keep the reply: payload's own
   `.coderabbit.yaml` is in the case heads (`docs/live-setup.md:33-34`), so CodeRabbit runs payload cases under that
   file. That is a stated limitation, not something to change.

Duration (estimate): about 7 hours of triggering if level 10 holds; about 39 hours at 1 per hour.

## 3. Collect (24 hours after the last trigger)
```sh
cd $TH && for R in medusa payload twenty; do
  jq -s 'map(select(.step=="pr-created")) | map({(.id): .number}) | add' $TS/run/open-prs/$R.resume.jsonl > $J/pr-map.$R.json
  node scripts/testset/collect-tool-reviews.ts --side dev --tool coderabbit --config scripts/testset/tools.json \
    --repo SunnyBagal/$R --manifest $TS/cases/dev/manifest.json --pr-map $J/pr-map.$R.json \
    --window-start <UTC time of the first PR opened in P1 or S1> --window-end <UTC now> --out $J/tools-$R
done
mkdir -p $J/coderabbit && cp $J/tools-*/coderabbit/*.json $J/coderabbit/
jq -s add $J/tools-*/coderabbit.status.json > $J/coderabbit.status.json
```
The collector writes one status file per `--out`, so each repository gets its own directory and the three are merged by
the last two lines. If the collector refuses a manifest with other repositories' cases, pass `--ids` with that
repository's ids.

Pass: `jq 'to_entries|group_by(.value)|map({(.[0].value): length})|add' $J/coderabbit.status.json` shows
`completed` ≥ 30 of 40, or the report states the limit that stopped it. `invalid-binding` must be 0.

2. Per repository: triggers, `reviewed`, `rate-limited`, `nothing`; highest level whose hour was all `reviewed`; median
   and maximum minutes to outcome; the remaining-allowance numbers CodeRabbit showed, if any.
3. The per-repository test: shared, not shared, or NOT RUN.
4. Reviews in the trailing 7 days at the first and at the last trigger, and whether the clean level changed during P1.

7. One line for D1: "rate at start N per hour, rate at end M per hour, shrank: yes / no; shared across repositories:

   schedule; P1 does not. If shrank is yes, F1 checks T0 ≥ last review + 7 days (076b item 3).

## 6. The three most likely ways to get this wrong
1. **Climbing faster than the ladder.** Ten triggers in the first hour can exhaust an allowance of 1 and leave nine
   rate-limit comments; the measurement is then "below 10" and nothing more. One level per hour.
2. **Counting a rate-limit comment or a walkthrough as a review.** Only a review object or an inline comment by the
   configured login is `reviewed`. The collector's status file, not the trigger log, decides `completed`.
3. **Letting Greptile run.** A `greptile` trigger, or an automatic review after opening a PR, spends held-out credits.
   The auto-review check in §1 exists for this.
