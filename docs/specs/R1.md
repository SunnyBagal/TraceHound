## 1. Batches
The runner takes one repository per invocation (`scripts/run-tracehound.ts:215`) and reviews cases in manifest order
(`:212`). A batch is at most 10 ids because a background process here is killed after 2 hours
(`docs/bench/results.md:232-233`). Each repository's ids, in manifest order, are cut into consecutive batches of nearly
equal size, larger first:

| batch | repository | cases |
|---|---|---|
| 1 | medusa | the first 8 of its 16 |
| 2 | medusa | the last 8 |
| 3 | payload | all 9 |
| 4 | twenty | the first 8 of its 15 |
| 5 | twenty | the last 7 |

```sh
cd $TS && for R in medusa payload twenty; do jq -r --arg r $R '[.[]|select(.repo==$r)|.id]|join(",")' cases/dev/manifest.json; done > $J/ids.txt
```
Write the five id lists into `$J/job.md` before the first call. They do not change afterwards.

## 2. One batch
```sh
# once, before batch 1:
L0=$(ledger); echo "L0=$L0 $(date -u +%FT%TZ)" >> $J/job.md
# every batch (IDS = that batch's list, R = its repository):
RUNCAP=$(echo "$CAP - ($(ledger) - $L0)" | bc)
cd $TH && node scripts/run-tracehound.ts --manifest $TS/cases/dev/manifest.json --clone $TS/repos/$R --ids $IDS \
  --out-dir $J/th --fixes off --contracts off --cache off --max-usd-per-case 0.40 --max-usd-run $RUNCAP             # dry run
# read the plan; then the same line with --execute, as a background process; note start and end (UTC) in $J/job.md
```
`RUNCAP` is the rolling rule of 076a: job cap − job spend so far. Do not add or subtract anything else.

**After batch 1, and before batch 2 starts (decision 076g item 7).** The operator writes batch 1's end time and the
job's ledger delta into `$J/job.md` and tells artu1. Sunny reads the console (balance, and usage by model); artu1
computes console drop ÷ ledger spend from Sunny's reading of 13 Nov (the one made the evening S1 ran) and writes the
ratio into `docs/budget.md`'s log. **Above 1.08: R1 stops; no further batch.** Batch 2 waits for that line (as
`.agents/STATE.md` has it since `e7db9bb`); artu1 may let it start earlier and logs that (076g item 8). A reading
taken minutes after a batch can miss charges that arrive later, so step 7 of §3 stays.

After each batch, before the next:
1. Exit code: 0 all ok; 1 a case `failed` or hit its cap; 3 the runner stopped before a case; 2 refused (nothing
   spent; fix the input and repeat). (`scripts/run-tracehound.ts` header, "Exit codes".)
2. `for f in $J/th/*.json; do jq -r '[.case, .status, (.review.chunksFailed // 0), (.usage.ledger.costUSD // 0), .diff.chars] | @tsv' $f; done`
   (record fields: `scripts/run-tracehound.ts:479-491`).
3. Ids the runner did not start (exit 3) go to the **front of the next batch of the same repository**; if there is no
   next batch, they form one more batch.
4. A case with status `failed` or `cap` is rerun **once**, after the last regular batch, with the same line plus
   `--rerun --ids <those ids>` (one invocation per repository). The rerun writes `<id>.r2.json`; the rerun's record is
   the official one (policy `official_attempt: last`). A case that fails twice is a miss. There is no third attempt.
5. If `RUNCAP` falls below $0.40 the runner refuses (`run-tracehound.ts:153`). Stop. Report which cases did not run.
   Do not raise the cap and do not use unallocated money.

## 6. The three most likely ways to get this wrong
1. **Starting a second paid process while a batch runs.** The run cap is a ledger delta; any other call counts against
   the batch and can stop it early (`run/out/bunny.caps-check.md`, "Limits"). One paid process at a time, including
   judging (a rule since decision 076c item 1; no code enforces it).
2. **Rerunning for a better result.** Only `failed` and `cap` cases are rerun, once. A case that ended `ok` with a
   failed chunk or zero findings is scored as it is (decision 068, partial reviews).
3. **Judging more than A0 here.** A1, A2, the second judge and the two tools' rows belong to L1's $0.40 line. Judging
   them under R1 breaks both envelopes and hides L1's real cost.
