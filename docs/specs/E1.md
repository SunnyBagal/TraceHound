## 2. L2: does a plain redraw recover a failed chunk? (reliability test, cache bypassed)
**Hypothesis under test (audit C076):** after an invalid or empty reply and a failed append retry, redrawing the
original request (reasoning on) returns a valid reply for about half of the lost chunks. Evidence that it might: on the
074 hard chunks 15 of 42 first draws were valid (`run/out/bunny.plan-audit.md` §5). Evidence that it might not: those
chunks were selected for failing, and one request was empty in all three runs.

### 2.1 The set
Every reviewer chunk with `status: "CHUNK_FAILED"` in R1's **official** records, both reviewers:
```sh
for f in $R1/official/*.json; do jq -r '.case as $c | (["review-diff-v1","review-ctx-v1"][] as $s | .lineage[$s].review.chunks[]? | select(.status=="CHUNK_FAILED") | [$c,$s,.index] | @tsv)' $f; done | sort -k1,1 -k2,2 -k3,3n > $J/l2.failed.tsv
```
(`$R1/official/` holds one record per case, R1 §3 step 1. The lineage keeps each stage's whole output under the
stage's name, `scripts/run-tracehound.ts:417-420`.) n = number of lines.
- **n < 4:** NOT RUN. No call, no change. Report n and the failed-chunk rate (n ÷ all reviewer chunks). Stop here.
- **n > 11:** take the first 11 by case id, then chunk index (076a "Caps" item 6); the gate applies to those 11.

### 2.2 The script (bunny creates it): `scripts/testset/redraw-failed.ts`
```
node scripts/testset/redraw-failed.ts check --records <dir> --manifest <f> --repos <dir> --failed <tsv> --out <dir>
node scripts/testset/redraw-failed.ts run   --records <dir> --manifest <f> --repos <dir> --failed <tsv> --out <dir> [--draws 2]
node scripts/testset/redraw-failed.ts report --out <dir>
```
```ts
export interface FailedChunk { case: string; stage: "review-diff-v1" | "review-ctx-v1"; index: number }
export function readFailed(tsv: string): FailedChunk[];                       // order kept; refuses > 11 rows or duplicates
export async function firstRequests(c: Case, repoDir: string): Promise<Record<FailedChunk["stage"], ChatRequest[]>>;
export function isValid(content: string): boolean;                            // parseReviewReply(content, DEFAULT_PARSER).ok
export interface Draw { chunk: FailedChunk; draw: 1 | 2; valid: boolean; empty: boolean; finishReason: string | null;
  outputTokens: number; costUSD: number; wallMs: number; error?: string }
export function gate(draws: Draw[], n: number): { n: number; recovered: number; share: number; verdict: "PASS" | "FAIL" };
```
Rules:
1. `firstRequests` builds each chunk's **first** request the way the pipeline does, by running the real
   `reviewPull` / `reviewPullWithContext` against a capturing client, as `capturedFirsts` does in
   `scripts/bench/hard-chunks.ts:139`. It does not rebuild prompts by hand. Input: the manifest's title and
   description and `git diff --no-color --no-ext-diff --no-textconv --find-renames --src-prefix=a/ --dst-prefix=b/ <base> <case head>` from the clone, the diff command the runner uses (`run/out/bunny.audits.md` (a)).
2. `check` ($0, no call): for every failed chunk, the rebuilt request's diff sha256 must equal the record's
   `diff.sha256`, and the chunk index must exist with the record's `files` and `diffChars`
   (`packages/analyzer/src/review/review.ts:202`). Any mismatch: exit 2. `run` refuses unless `check` passed in the
   same `--out`.
3. `run`: for each chunk, `--draws` (default 2) calls of that first request, unchanged (temperature 0, `max_tokens`
   32,000, reasoning on; `review.ts:205-207`), through `TokenFactoryClient` **with no response cache: neither read nor
   written** (as 074, `hard-chunks.ts:3`). Sequential. Budget from the environment (`capsFromEnv`). A request error
   is a draw with `valid: false` and `error` set; it is not retried.
4. `valid` = `parseReviewReply(content, "lenient").ok` (`review.ts:121`, `DEFAULT_PARSER`), the test the pipeline
   applies to a first reply at `review.ts:231`. `empty` = the content is empty after trimming. A non-empty reply is not
   necessarily valid.
5. If the budget refuses a call, stop; chunks without both draws are **incomplete** and the verdict is `INCOMPLETE`,
   never computed on the chunks that happened to finish.
6. stdout: counts only. `<out>/draws.jsonl` keeps the per-draw rows; reply bodies go to `<out>/replies/` and are never
   printed. Never overwrites.
7. Tests (fake transport; no network): the gate table below; `check` refusing a changed diff; no cache read and no
   cache write (a cache spy sees 0 calls); budget stop → `INCOMPLETE`; > 11 rows refused.

| fixture for `gate` | expected |
|---|---|
| n = 4; chunks valid in a draw: 2 | share 0.50 → PASS |
| n = 4; 1 | 0.25 → FAIL |
| n = 5; 2 | 0.40 → FAIL |
| n = 11; 6 | 0.545 → PASS |
| a chunk valid in both draws | counted once |

### 2.4 If L2 passes: the change bunny lands (after decision 077, before R2)
In `packages/analyzer/src/review/review.ts` and in `packages/analyzer/src/review/review-ctx.ts`, which has its own attempt loop (`:83-94`): after the
append retry fails (`review.ts:243-250`), one **third attempt = the original first request, unchanged**. The chunk is
`CHUNK_FAILED` only if that also fails; `attempts` becomes 3 and `attemptsDetail` gets a third row.
- The third attempt must not read the response cache: it has the same cache key as attempt 1, so a cache read returns
  the failed reply again. Pass `readCache: false` for that call (`packages/analyzer/src/llm/client.ts:169`).
- Attempts 1 and 2 keep their request bytes: `packages/action/test/pool-verify-identity.test.ts` stays green with no
  snapshot change. New tests: third attempt's request equals attempt 1's; valid third reply → chunk `OK`, `attempts: 3`;
  invalid → `CHUNK_FAILED` with all three reasons in `failure`; a chunk that succeeds on attempt 1 or 2 makes no third call.
- Default 3 attempts everywhere the pipeline runs (decision 076: "default 3 attempts"). No flag to turn it off is
  needed before the freeze; codex GO; the per-case cap of $0.40 is unchanged.

## 8. The three most likely ways to get this wrong
1. **Reading the gate generously.** "+2 with far fewer comments" is a tie; A0 stays. A gate is not re-argued after the
   numbers exist, and a second look with another judge or another cap is a new experiment that is not in the budget.
2. **Letting the cache answer the redraw.** A redraw served from the cache "fails" every time; a third attempt that
   reads the cache never recovers anything. L2's script uses no cache; the product change uses `readCache: false`.
3. **Computing L2's verdict on the chunks that finished.** If the budget stops the run, the verdict is `INCOMPLETE`.
   Dropping the unfinished chunks biases the share upward, because cheap (short) replies finish first.
